# TraceGuard：Hackathon 产品展示评审与演示建议

评审日期：2026-10-23（Asia/Shanghai）。

依据：[《POLYV 2026 Hackathon资料提交指引》](https://alidocs.dingtalk.com/i/nodes/lyQod3RxJK3R47ezsY5maZ5LJkb4Mw9r?utm_scene=person_space)正文，以及本仓库 [TraceGuard 交互原型](TraceGuard-交互原型.html)的实现。此次检查为正文与本地实现对照，未重新逐屏进行视觉验收，也未连接数据库验证实时链路。

## 1. 指引实际要求

- 演示视频建议 2–3 分钟，参考内容为：作品是什么、为什么做、实现效果与价值、下一步做什么。
- 视频与源码提交截止时间均为 **2026-10-24 09:29**。
- 视频通过团队专属频道登录保利威平台提交，具体上传步骤另有链接指引。
- 源码要求上传至个人 GitHub，再将链接发给楚欣。
- 若使用保利威 API/SDK，提交源码时需同步说明；文档称评委会结合实际情况在技术层面酌情加分。

该文档是资料提交指引，没有给出完整评分维度和权重。以下优先级是针对 TraceGuard 的产品展示建议，不是赛事官方评分标准。

## 2. 当前已有的展示基础

原型已覆盖风险大盘、告警中心、个人/视频计分卡及规则编辑器。已有分数解释、身份依据、证据状态、复核记录、规则样例回放和本地版本保存，不需要为了演示再扩展顶层菜单。

三个现成案例可以直接构成演示材料：

| 案例 | 已有事实 | 展示价值 |
| --- | --- | --- |
| 高速拉片 | 补充样本在 10 分钟成功访问 7,200 秒去重媒体内容，12 倍；720/720 个分片、递增 100%、间隔 CV 0；723 次工具特征请求覆盖 3 个阶段 | 展示同一活动的多种行为证据；当前应用分别告警，跨规则 S75 仍是计分卡候选演算 |
| 视频失败集中 | 同口径 500 次 TS 鉴权，450 次失败，失败率 90%；R7 只计异常分 | 展示异常高不等于盗版嫌疑高，避免将故障扩大解释为用户盗版 |
| 身份待核实 | 关联 token 有风险，但没有可归因到个人的独立行为依据 | 展示数据不足保留未知，关联身份不自动视为实际操作者 |

当前浏览器使用预置虚构场景及本地状态；数据标签已作说明。特征 SQL 和验证脚本是另一个实现部分，尚不能仅凭两者同时存在，就声称已打通在线日志、自动抽取、规则评分和告警入库。

## 3. 主要缺口与建议

### P0：评委需要先知道谁遇到了什么问题

当前打开即进入运营工作台，产品定位主要散落在标题与页面说明中。评委若不熟悉鉴权日志，很难在十秒内理解需求。

建议在视频开场或大盘顶部说明：

> 面向视频内容运营与风控人员，把分散的播放、鉴权和内容访问日志，变成可解释、可复核的异常内容获取线索。

接着用一个问题引入：“凭证合法、鉴权通过，是否就意味着访问行为正常？”再解释人工逐条查日志为什么难以识别持续高速获取、跨环境交错等组合行为。此处避免宣称能确认盗版或绕过 DRM。

### P0：需要一条固定案例，而不是依次参观四个菜单

当前演示指南介绍各模块，但没有绑定一个案例和最终处理结论。评委需要记住的是一次判断过程。

建议固定主线：大盘发现高危险线索 → 打开高速拉片告警 → 看证据 → 解释计分 → 留下复核依据。可在现有大盘加入该案例的快捷入口，或录制时预置筛选条件；不另建新模块。

演示入口应能恢复固定初始状态，避免此前的规则修改或复核操作影响录屏。现有重置功能可以作为录制准备步骤。

### P0：证据目前以文本为主，缺少“为什么可信”的直观画面

详情已显示命中事实，但“7,200 秒、12 倍、98%、CV”等指标对首次接触者仍偏抽象。

建议在现有告警抽屉中补充两类展示：

- 内容获取条：10 分钟观察窗口，对应 120 分钟去重内容；注明这是内容访问证据，不等同于实际观看。
- 简短证据时间线：选定窗口、关联账号/会话、相关视频、分阶段事件及来源。点击后才展开分母、未知量和原始记录引用。

数字应来自同一窗口、同一主体及同一来源口径。鉴权通过和 CDN 响应分开展示，缺失字段显示未知，媒体内容按时间轴去重。不要为了视觉效果补造事件级细节。

### P0：把“少误判”作为对照展示

现有双分与未知状态设计是产品区别点，但若演示只展示一个高分案例，评委会把它理解为阈值告警。

建议主案例之后用约 20 秒展示视频失败案例：异常 A=50，嫌疑 S=0；解释“先排查鉴权或服务问题，不将失败自动解释为盗版”。身份待核实案例可留作答辩补充，或替换此对照；三分钟内不必把所有案例都演完。

### P0：需要清楚交代当前实现与下一步

现有虚构数据标签应继续保留，同时在视频结尾列出可核对的实现范围：

- 已有：交互工作台、预置场景、浏览器端计分模拟、复核状态与本地规则版本；基础事件契约、公共视图及特征 SQL。
- 需用执行结果证明：当前数据集规模、特征验证通过数量、查询耗时。仅使用可核实报告，不将历史记录直接当成当前执行结果。
- 下一步：接入来源数据，按规则窗口调度特征计算，持久化特征与评分快照，贯通告警生成和复核反馈，再进行真实数据校准。

若没有实际调用保利威 API/SDK，不因产品围绕视频风控就声明已集成。若有调用，应展示实际触点与其作用。

### P1：复核以后，用户下一步做什么还不够明确

当前可确认风险、标记误报、开始复核和挂起观察，并记录依据。业务闭环还可在现有抽屉中显示：建议下一步、处理责任人、待补证据及复查时间。

演示可先通过复核依据表达下一步行动，例如“已确认异常内容获取线索，交由业务核对批量下载授权”。真实封禁、撤销凭证等操作若未接通，不展示为已执行成功。

### P1：价值缺少可比较的结果

目前能看出告警数量，尚缺少有依据的效率或判断价值对照。可以用同一小组样例比较“人工逐条查看”和“聚合特征解释”的操作步骤，或实际计时后报告复核用时。

无实测时，描述为“集中呈现分散证据、区分故障与嫌疑、保留未知状态”，不编造节省百分比、准确率或已避免损失。若展示复核率、误报占比等指标，应同时明确样本数和人工标注口径。

### P1：规则编辑需要展示修改带来的效果

现有编辑、校验、回放和本地版本保存已可交互。展示时优先呈现“同一样例、同一观察窗口，修改前后命中与分数变化”，而不花时间逐项讲 AND/OR 和字段名。

可增加一个未命中或合法行为样例作对照。历史告警继续显示触发时快照，新配置只影响新模拟；不要把本地保存演示成生产规则发布。

## 4. 建议的三分钟讲述顺序

| 时间 | 画面与操作 | 要传达的意思 |
| --- | --- | --- |
| 0:00–0:20 | 开场问题与产品一句话定位 | 谁在用，为什么需要它 |
| 0:20–1:15 | 大盘打开高速拉片案例，查看内容量与证据 | 从分散日志中找到可解释线索 |
| 1:15–1:40 | 查看计分卡，说明同事实去重、证据封顶和双分 | 分数有依据，且不代表盗版概率 |
| 1:40–2:00 | 打开视频失败案例 | 异常与盗版嫌疑分开判断 |
| 2:00–2:25 | 保存主案例的复核依据与下一步 | 用户能够完成一次判断和交接 |
| 2:25–2:45 | 如时间允许，展示一个规则回放前后变化 | 规则可解释、可验证；不逐项介绍编辑器 |
| 2:45–3:00 | 已实现范围、价值与下一步 | 原型完成度可信，后续路径明确 |

若录制超时，优先缩短规则编辑操作，保留主案例、对照案例和复核结果。技术表名、SQL 目录和逐个特征编号留在源码说明或答辩材料中。
