# 原始事件采集缺口分析

核查日期：2026-10-22。对象：`DA_CLICKHOUSE_DB_TEST` 的 `da.dwd_vod_play_events`。所有数据库操作均为只读；未修改表、数据或业务代码。

依据：[基础特征提取设计](计分规则-修订稿.md)、[计分卡 v0.2](计分卡-v0.2.md)、本次实际表结构/聚合数据，以及本地 `vod-hls-aggregate`、`da-deliver` 的审计与投递代码。

## 1. 结论

当前具备“token 创建/取得、密钥鉴权、分片回源鉴权”三类审计事件，但还没有覆盖“播放地址/清单访问、密钥最终响应、CDN 媒体实际访问、完整授权生命周期、可信播放状态”等证据。即使三种事件都存在，也不能据此还原完整播放或内容获取链路。

缺口分三类，处理方式不同：

1. **需要接入/补充的原始事件**：播放地址与媒体清单请求、CDN 媒体访问、请求最终结果、授权续期/撤销及播放状态等。
2. **本地上游代码已具备但 DWD 未保存的信息**：失败原因、token 有效期、绑定观众、请求 IP 与绑定 IP 的区别、appId、pid 等。先修数据契约与落库，不一定需要另造业务事件。
3. **已有原始字段可以加工的信息**：UA 分类、IP 地域、时段标签、观测失败率、token 关联环境数等。派生列为空不等于原始事件缺失。

“缺失”在本文指目标表以及已检查本地链路未提供相应证据，不表示这些数据在全公司所有日志/其他表中均不存在。本次没有获得同库相关表清单，也没有直接读取 Kafka/线上原始审计日志；本地代码存在字段不等于已确认测试实例部署了同一版本。

还需新增或补全以下来源元数据，它们不一定是新的业务事件：

- event_id/request_ref、原始日志引用、Kafka topic/partition/offset、来源实例、schema/解析版本。消费者已经能拿到 ConsumerRecord，但当前没有入库这些位置，缺少稳定重放去重依据。

- 结果层次：auth_result、final_http_status、delivery_result 分开；未知结果单列，不能统一压成失败。

## 5. 本地链路揭示的具体口径问题

### 5.1 消费者只允许三种事件

`da-deliver` 的消费者分别处理 TOKEN_CREATE、HLS_KEY_VALIDATE、TS_VALIDATE，其他 eventType 直接 continue；且先按 `isPriracyTraceAnalyzeStats` 客户集合过滤。即使上游新增清单或传输事件，不调整接入契约也不会进入此表。分析范围必须标明启用客户和配置时段，不能当成全平台所有请求。

### 5.2 success 不能一列包办全部结果

本地消费者使用 `asBoolean(false)`，success 缺失时会写 0，与“未知不当失败”的特征约定不一致。实际表另有 32 条非 0/1 TS 记录，说明不能凭这份代码解释所有历史写入路径；生产版本和历史来源需核对。现有 0/1 数据也无法恢复曾被默认 false 的原始未知结果，需原始日志回查。

`HLS_KEY_VALIDATE` 在鉴权完成时记录成功，但 PtsKeyController 之后还会读取切片信息；读取不到会返回 404。其他 KEY 输出路径也可在鉴权后失败。因此 KEY.success=1 不是最终成功返回密钥。

### 5.3 IP 与 UA 存在角色混用

KEY 的实际 requestIp 与绑定 viewerIp 在原始对象中是两列，当前落表时后者可覆盖前者。泄漏 token 的请求即使来自另一个 IP，也可能在 KEY 行看起来仍是原绑定 IP，直接影响 R4B/R5。TS 则使用自己的请求 IP 口径；不能跨事件类型直接把这些值当作同一种客户端 IP。

TOKEN_CREATE 的请求 UA 经常属于客户服务器/HTTP 库。把它与播放器 KEY/TS 的 UA 比较，容易制造“环境突变”；把它直接判为工具下载，也容易误报。首版 R4B 优先在同一 TS 来源与已核实 IP/UA 语义下提取。

### 5.4 viewer_id 非空不代表已识别个人

创建逻辑会在观众未提供时使用默认 viewer_id。KEY/TS 的 viewerId 来自 PlayToken，不是当前发起者的独立认证身份。当前表又不保留 identity_basis、tokenViewerId 与是否默认值，不能仅用非空 viewer_id 生成确定的本人行为嫌疑。

本次没有统计默认 viewer 值的实际占比，不以源码常量出现推断表中一定有多少此类记录。

### 5.5 创建、续期和资源角色需要拆分

PlayTokenManager.createToken 在 token 已存在时可以复用 token，同时重写 createdTime 和 expiredTime；仍由 TOKEN_CREATE 记日志。因而 TOKEN_CREATE 不必然是一个新 token，当前 tokenCreatedTime 的名称也不能直接解释为该 token 的历史首次创建时间。

TS 审计中的 userId：存在 PlayToken 时取 token.userId，否则可能取 TS URL 解析用户；videoPoolId 则取目标 TS 视频。跨账号尝试时，这两个字段可能分别属于凭证客户和资源目标。特征层应同时保留双方角色，不能不加辨别地把 user_id 当目标视频租户。

TS 鉴权还存在“校验开关关闭直接通过”“TS URL 解析失败但按 token 通过”等本地代码路径。需要记录 validation_mode、scope_check_performed/结果与配置版本，才能判断一次 success=1 究竟验证了哪些条件。

### 5.6 有片号不等于有准确内容量

segment_index 大部分可用，但表没有媒体清单、总片数、实际分片时长、清晰度/轨道/资源版本和媒体时间区间。只能先计算观测片号/请求量；准确覆盖、跨清晰度去重媒体秒数、完整输出量仍缺数据。

本地旧方案写过“约每十片一次、采样 Tag ×100 秒”的估算；本次未定位 CDN/文件服务侧实际触发策略，也没有实查源采样配置，不能据此认定它是随机采样或准确还原所有片段。审计日志服务本身仅输出日志，没有在该类中实现 1/10 抽样。

## 6. 必须补充的维度数据：不应都叫原始事件

| 数据 | 推荐来源 | 用途 |
| --- | --- | --- |

## 7. 对 10 类规则的实际可用性判断

| 规则 | 现阶段可做 | 当前阻塞的证据 |
| --- | --- | --- |
| R1 链路异常 | 观察 TOKEN/KEY/TS 的时间线 | 清单/地址事件、最终结果、有效期历史、全链路关联及采集覆盖；不能把“无记录”直接判缺失 |
| R2 拉片速度 | TS 观测量、片号集合和明确标注的估算线索 | 清单时间轴、采样/回源覆盖、媒体传输观测；暂不能当准确观看/完整下载量 |
| R3 多视频并发 | 窗口内访问过的视频数 | 可信播放状态或已校准的请求活跃模型；play_id 全空 |
| R4A 范围外复用 | 同 token 关联视频、成功/失败结果 | 当时授权范围/有效期、failReason、凭证与资源角色；多视频本身不等于越权 |
| R4B 多环境使用 | 同一 TS 来源的 token/IP/原始 UA、观测交错与通过数 | UA 归一化、IP 来源确认、合法多端策略、凭证归属/实际访问者区别；样本已观察下界可保留 |
| R5 环境变化 | IP/原始 UA 观测与变化 | IP/UA 角色拆分、客户端解析、地区补充、默认身份识别；不能输出物理设备数 |
| R6 机械访问 | 片号样本与样本间隔 | 完整序列、清单及播放操作；样本规律不能充当完整规律 |
| R7 失败过多 | 按视频/阶段统计明确 0/1 的观测失败率；其他结果单列 | failReason、完整入口失败与最终响应、未知处理、采样覆盖；不能直接归因盗版 |
